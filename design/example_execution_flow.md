# Example Execution Flow & Sequence Design

This document provides a concrete example showing how the macro-blueprint and micro-gossip-routing definitions are structured.

---

## 1. The Macro-Blueprint (`agent.flow.yaml`)

This is the top-level blueprint processed directly by NeuroCore. It defines only the global orchestrators, maintaining a clean macro flow of **`start` $\to$ `coordinator` $\to$ `end`**.

```yaml
name: "math-theorem-proving-agent"
version: "1.0"
description: "Orchestrate research and verification of mathematical theorem proving models"

components:
  - name: flow-start
    type: start
    config:
      validate_schema: true
  - name: task-coordinator
    type: coordinator
    config:
      persistence_root: "/home/ubuntu/neurocore-skills/runs/"
  - name: flow-end
    type: end

flow:
  type: sequential
  steps:
    - component: flow-start
    - component: task-coordinator
    - component: flow-end
```

---

## 2. The Micro-Gossip Routing Plan (Task-Context JSON/YAML)

When `flow-start` initializes, it passes the task requirements. The `coordinator` calls the `planner` to draft a detailed execution plan. The plan contains a **Task Execution Graph** specifying the tasks, their execution steps, and how results should route through verification skills.

Here is an example of the structured JSON/YAML task plan generated by the Planner:

```yaml
plan_id: "run_98231_theorem_proof"
goal: "Research and verify the SMT expression: x > 2 and y > 2 => x * y > 4"
artifact_directory: "/home/ubuntu/neurocore-skills/runs/run_98231/"

execution_steps:
  # Task 1: Research and compile background papers
  - step_id: "step_01_research"
    description: "Search arXiv and compile paper summaries on transformer math proof models"
    assigned_worker: "worker"
    routing:
      sequence:
        - "researcher"  # Step 1: Research query
        - "writer"      # Step 2: Write research summary
        - "reviewer"    # Step 3: Adversarially review summary
        - "judge"       # Step 4: Quality validation gate
      on_success: "step_02_verification"
      on_failure: "error"

  # Task 2: Math Verification
  - step_id: "step_02_verification"
    description: "Verify the SMT formula: x > 2 and y > 2 => x * y > 4"
    assigned_worker: "worker"
    routing:
      sequence:
        - "researcher"  # Step 1: Query formal proof contexts
        - "worker"      # Step 2: Formulate SMT input
        - "math_verifier" # Step 3: Run Z3 check
        - "reviewer"    # Step 4: Critique proof formulation
        - "judge"       # Step 5: Final validation gate
      on_success: "complete"
      on_failure: "error"
```

## 3. Dynamic Gossip Execution Trace

During execution, when the Coordinator launches a step:

1. **Step Dispatched**: Coordinator posts a gossip message:
   ```json
   {
     "sender": "coordinator",
     "recipient": "worker",
     "message_type": "execute_step",
     "payload": {
       "step_id": "step_02_verification",
       "artifact_path": "/home/ubuntu/neurocore-skills/runs/run_98231/step_02/",
       "task_prompt": "Verify the SMT formula: x > 2 and y > 2 => x * y > 4",
       "sequence": ["researcher", "worker", "math_verifier", "reviewer", "judge"]
     }
   }
   ```

2. **Sequential Routing**: The Worker begins executing. It delegates research by sending a gossip request to `researcher`. When `researcher` finishes, it inspects the `"sequence"` list in the payload and forwards the context directly to the next peer:
   * `researcher` completes $\to$ sends message to `worker`
   * `worker` creates SMT script $\to$ sends message to `math_verifier`
   * `math_verifier` runs Z3 check $\to$ sends message to `reviewer`
   * `reviewer` creates critiques $\to$ sends message to `judge`
   * `judge` evaluates $\to$ sends message back to `worker` (or coordinator on success).

This peer-to-peer delegation keeps the top-level blueprint completely static, while giving the higher-order agent complete control over task routing.
